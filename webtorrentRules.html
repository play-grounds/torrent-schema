1info_hash, peer_id and offer_id are binary strings of exactly 20 charactersws-bad-idlength == 20 and every char code < 256
2an announce reply carries an intervalws-no-intervalinterval > 0 unless 'failure reason'
3an offer is announced to one tracker onlyws-offer-reusedeach tracker gets offers made for it; the same offer on two trackers reaches the same peer twice, it answers twice, and two connections with one set of ICE credentials break each other (found the first time this page announced one offer to two trackers)
4an answer names an offer this peer made and has not yet usedws-unknown-offeroffer_id in outstanding offers; else ignore the answer
5a forwarded offer or an answer is for a torrent this peer announcedws-wrong-torrentinfo_hash in announced
6an offer's description is of type 'offer' and an answer's of type 'answer'ws-bad-sdpoffer.type == 'offer'; answer.type == 'answer'
7once connected, the data channel carries the wire protocol exactly as over TCPwire-bad-handshakethe first 68 bytes on the channel are a Handshake for the same info_hash
8a description sent through the tracker does not say tricklews-tricklethe SDP has no a=ice-options:trickle line: the protocol carries one whole description each way and no candidates afterwards, so the line promises what cannot come; browsers put it in by default and browser WebTorrent strips it (found when no stranger answered offers that kept it). Node webtorrent with wrtc leaves 'a=ice-options:ice2,trickle' in (an offer of its captured 8 Oct 2026, test/vectors/webtorrent/offer-forwarded.json) and still connects, so the rule is advice to the sender, not grounds to refuse an offer
